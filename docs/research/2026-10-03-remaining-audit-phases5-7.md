## Phase 5: import allocation and readable failures

The importer probes the header before decoding, then the modal owns one decoded image and its estimated RGBA reservation. It no longer decodes once in the file reader and again in the modal. Decode dimensions must match the admitted header, allowing a width/height swap for image orientation. Source decode, image analysis, sampling, output, display and slicing work reserve estimated memory before allocation. Exclusive import canvases are cleared and released after replacement, failure, cancellation or unmount. Artwork registry, rollback and practice surfaces retain their ownership contracts.

Display previews have a longest dimension of 1,024 pixels. Pixelize sampling uses at most 2,048 pixels per axis before the existing processing pipeline; this can change sampling on large source images. The modal uses a canvas preview without retaining a duplicate PNG data URL. The processing pipeline clears scratch surfaces and bounds its true-color swatch collection to the 32 colors it already returned. Color-reduction output reserves a conservative allowance for quantization objects; this is an estimate rather than a measurement of JavaScript object size.

Sprite slicing reads directly from the decoded original. Empty-cell checks use tiles no larger than 256×64 pixels with the existing alpha-greater-than-five policy. A display downsample therefore cannot erase a one-pixel detail and misclassify its original cell. Sources up to 4,194,304 pixels permit exact preview analysis; larger sources defer the count to import and label that fact. Blank holds remain included by default. Successful confirmation copies sliced pixels into artwork before releasing the modal's exclusively owned temporary frames.

Project file parsing now uses the existing 50,000-node metadata ceiling in addition to byte/depth admission. Typed SafeJson failures and legacy header-probe errors receive readable import advice; the original technical error is logged separately. Shared memory errors use operation-neutral advice rather than assuming the operation is an export.

Limits remain: browser image decoding and GPU memory are not measured or capped by this reservation system; the input data URL and transient JavaScript allocations still exist. Original-cell checking and pixelization can perform synchronous work. These changes do not qualify low-memory physical devices or certify every image profile/orientation combination. [Current import guide](../guides/studio-workspace.md#bring-in-an-image), [storage contract](../contracts/storage.md).

## Phase 6: APNG responsiveness, compression and cleanup

APNG frame composition and encoding now yield to browser tasks between frames and honor cancellation. Native `CompressionStream('deflate')` provides zlib-framed output; missing support or an unsupported constructor falls back to the existing stored-block encoder. Codec failures after support detection remain failures rather than silently switching encoders. RGBA content, chunk checksums/sequence numbers, authored holds and loop semantics remain covered by independent decoding and existing format tests. The format choice follows the [WHATWG compression standard](https://compression.spec.whatwg.org/); task-level yielding follows the [HTML timer model](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers).

The export modal reserves fresh frame composition before allocation, exposes exporting state before starting work, and releases these exclusive canvases/reservations on success, failure and cancellation. Capacity failures offer frame/scale advice; rendering or codec failures offer a retry or another format. A single frame's extraction and fallback compression remain synchronous. Output still accumulates chunks into a Blob; this is not a worker, streaming sink, fixed compression-ratio promise or measured latency guarantee. [Current export contract](../contracts/exports.md).

## Phase 7: bounded diagnostics and remaining small boundaries

Rejection reporting handles circular objects, BigInt and throwing getters/proxies with bounded serialization. Capture deduplicates the same bounded kind/message/detail/route for ten seconds, admits a burst of 20 with 60/minute refill, and permits at most 20 pending database writes. Writes and pruning are serialized. Rejected excess events are dropped rather than queued indefinitely. This bounds admitted work; it is not an IndexedDB throughput benchmark.

Opted-in reporting batches at most ten entries after five seconds. Additional entries remain eligible for local storage but overflow of the current relay batch is dropped. Consent is rechecked after storage and before sending; revocation clears pending batches and removed/invalid persisted settings do not inherit an earlier opt-in. Reports are best-effort and can be lost on page close. Logging remains local by default, with free-text privacy limits unchanged.

The relay rejects malformed/oversized event batches, forwards selected bounded fields, preserves the reported client version and includes a separate server version. Body chunks are concatenated once within the existing 64 KiB limit. Configured HTTPS forwarding rejects redirects, consistent with the [Fetch redirect model](https://fetch.spec.whatwg.org/#concept-request-redirect-mode). This does not establish authentication, a global distributed quota or arbitrary-destination SSRF certification; upstream/proxy trust remains operator-owned.

Manual signaling validates peer ID, offer/answer SDP and typed ICE candidate fields before applying them to WebRTC. Existing encoded-token size admission is retained, with a 4,096-node traversal ceiling and a 256-candidate workload policy. A host invite must carry an offer; a guest reply must carry an answer. These are application ceilings, not universal [WebRTC limits](https://www.w3.org/TR/webrtc/#rtcicecandidate-interface). Forty-candidate and maximum-admitted cases remain covered.

The global skip link targets the current page: landing content uses `#top`, and Studio/practice use `#main-workspace`. Targets are focusable, and the link has an explicit zero tab index. Windows WebKit skipped the ordinary link in the initial browser run; Alt-Tab also failed. A controlled two-page probe showed that adding `tabIndex=0` made the first Tab press focus it. WebKit's [anchor focus implementation](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/html/HTMLAnchorElement.cpp) distinguishes explicitly focusable elements from its link-navigation preference. [Apple's keyboard guidance](https://support.apple.com/guide/safari/keyboard-shortcuts-and-gestures-cpsh003/mac) explains Safari's link-navigation setting, but did not alone predict this Windows runner's behavior. The product was fixed and the original Tab/Enter assertions retained. This is automated browser evidence, not an assistive-technology study.
