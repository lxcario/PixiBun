## Engineering changes

Motion editing has numeric position/rotation/pivot/frame controls, Reset Pose, bounded parameter Undo/Redo and one history step per completed gesture. The engine, UI and saved format share the 2–30 frame range. Motion owns workspace Undo/Redo until Cancel or Bake. Stale-source parameter replay refuses.

Browser profiles found main-thread work in motion previews and multi-frame baking. The follow-up adds a dedicated motion worker, one active/one replaceable queued preview, source/session validation before display, timeout/cancellation cleanup and staged asynchronous baking with atomic publication. Other compute workers remain independent. Main artwork stays visible until a valid initial preview is ready. The source cel duration now governs both preview and baked timing. Tools also exposes whole-layer capture without requiring a selection.

Async bake validates document/source/selection/motion ownership while allowing harmless autosave cleanliness and view-only zoom changes. Cancellation and source changes still discard unfinished staging. Worker tests cover this distinction. HUD and inspector Bake share the same owner and stop the preview clock before starting.

The fresh production audit identified `sharp` 0.35.4 and `source-map-js` 1.2.1. Compatible lockfile patches resolve them to 0.35.5 and 1.2.2 respectively, including Sharp's matching native/libvips packages; package declarations and Next.js 16.3.8 are unchanged. The patched production audit reports zero advisories. The upstream [Sharp advisory](https://github.com/advisories/GHSA-wq5f-xc86-pv6w) concerns its SVG decoder dependency under specific Linux runtime conditions; the [source-map advisory](https://github.com/advisories/GHSA-68fv-2mgg-jv7q) concerns unvalidated indexed-map offsets. No direct application imports of either parser were found; this review does not prove every framework path unreachable. The patch removes the known affected versions without a general dependency upgrade.

## Controlled local responsiveness

Before and final-candidate profiles each used nine fresh Chromium contexts: three repetitions at 64, 128 and 256 pixels per axis. The original synthetic project has four cels, one color layer per cel, 125 ms holds and a selected central area. Hardware was an Intel Core i5-12500H; Chromium 151.0.7922.34 ran headless at 1600×1100 without simultaneous owned browser workloads. Browser/automation pacing and intentional playback waits are included in completion spans. No CPU throttling, physical pen measurement, whole-heap measurement or INP measurement was performed. The final rotation profile also waits for worker preview readiness; the earlier synchronous preview completes before its post-action animation frames.

| 256×256 workflow | Before median completion | Final median completion | Before → final median long-task count | Before median longest task |
| --- | --- | --- | --- | --- |
| Five rotation edits | 458 ms | 332 ms | 5 → 0 | 97 ms |
| Two-second motion playback | 2,167 ms | 2,105 ms | 13 → 0 | 76 ms |
| Five-pose bake | 321 ms | 900 ms | 1 → 0 | 266 ms |

Long tasks exceed 50 ms. The measured benefit is reduced main-thread blocking, with increased bake completion time after the worker change; this profile does not isolate transfer, scheduling and rendering costs. Main-thread composition and per-cel canvas staging remain; these observations do not guarantee zero long tasks for every project or device. Full 64/128/256 drawing, timeline, save and export observations are retained with the comparison. The older raw profile label `bake-8-frames` was incorrect: capture used the default five poses. Raw files retain that label, while the comparison normalizes it to five and final instrumentation records the actual field value. An earlier profile overlapping browser verification is retained separately and excluded from the controlled comparison.
